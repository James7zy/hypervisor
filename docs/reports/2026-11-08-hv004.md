## 2. 过程事实（必须记录）

**研发子会话在 T3 收尾时超时（30 分钟上限）**，T1/T2 已提交，T3 的 guest 场景与 expect 留在
工作区未提交。架构师接手：逐行复核场景 → 重跑 `hcall` ×4 与全套 gate → 提交 `8047413`。
**复核时发现并修了一处研发漏掉的竞态**：`sched_vm_resume` 只重入队 `RUNNABLE`，漏了
`ON_PENDING`——与暂停竞争的 CPU_ON 会被 pick 丢弃后永久丢失，secondary 永不上线（`e9c434c`
+ host 用例，scheduler 34 → 60 断言）。

## 4. 架构师关卡②（2026-11-08）：PASS

Review 范围 `ac844e4..e9c434c` 五个提交 + 收尾文档。确认：

- 暂停 = 调度判据：`sched_loop` 在 pick 之后丢弃（`sched_pick` 未动，保持纯出队）；
  kick 分支与 tick 分支同形（先 EOI 再解栈、idle 窗口不 `hv_restore`）。
- 恢复的 `RUNNABLE | ON_PENDING` 语义与 host 用例；`BLOCKED` 不被唤醒。
- 权限走表项 `roles`（HV-005 的表项权限分支自此有真实覆盖），状态码 `EBUSY/EINVAL/EPERM/ENODEV` 齐全。
- 既有 12 场景 expect 只有 `hcall.txt` 追加；`-Werror` 零告警；架构边界与 offsets 通过。

**测试专家三条"必须记录"的处理**：

| 发现 | 处理 |
|---|---|
| **D1 kick 分支无回归门**：删掉后 `hcall` 仍全绿（量子 tick 兜底） | **接受并记录**：kick 是延迟优化（10 ms → µs），正确性由 tick 兜底；写进 ADR-0023 已知缺口，触发条件 = 出现需要亚量子级停止延迟的消费者 |
| **D2 文档说 `sched_pick` 丢弃，代码在 `sched_loop`** | **改文档**（spec F2 / ADR-0023 / plan T1）：丢弃点是 `sched_loop`，并说明为什么 pick 保持纯出队 |
| **D4 ADR-0023 未提交、无 devlog** | 本次提交补上（ADR + devlog + 本报告） |

另两条非阻塞（`ON_PENDING` 只有 host 覆盖；时序编排靠 1.30 s 裕量）已写进 ADR / devlog。

## 5. 已知缺口

- 异步生效，无确认协议（触发 = 首个"停稳后复用资源"的消费者）。
- `CREATED/READY/DESTROYED` 与事件通道未做（依赖 H2 页分配与 VM 创建/销毁）。
- kick 无独立回归门；`ON_PENDING` 只有 host 单点覆盖。
- 只支持 Service VM 发起；跨 VM 事件通知没有。
